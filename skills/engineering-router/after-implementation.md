# From implementation to pull request

Read from SKILL.md §6 when the implementation step is about to start. It holds everything from there to the open PR: the implementation's own review, the manual checklist, the reviews, security and fixes, verification, and the pull request with its run record. Execution and exceptional stops follow [autonomy.md](autonomy.md). How every review step runs, on the other family, is in [cross-family-review.md](cross-family-review.md).

## Check plan before implementation

Before briefing implementation or fixes, inspect the target's required checks and effective Git hooks (`core.hooksPath`, or its default hooks directory). Assign each required check to an execution point: focused checks during development, hook-owned checks at commit, and remaining checks before delivery. Pass that plan to the implementing agent.

When an enabled commit hook runs the required full suite, use its execution as the final full-suite check. Run focused tests during development and let the normal commit run the hook. Preserve the hook's actual command, output and environment in a log reachable by the reviewer; record each successful check with `scripts/state … check` against the resulting files. A hook configuration or a successful commit alone is not proof that a check ran. If its output cannot establish the required result, run and capture the missing check explicitly. Keep mandatory hooks enabled.

Check the final diff after the hook: formatting or other hook changes can invalidate a check that ran earlier. Reuse only results that still match their recorded files and environment, under the pull-request rule below. Done when every required check has observed passing evidence on the final changes; a planned hook run remains pending until observed.

## The implementation's own review

When the implementation skill calls a review itself (e.g. `mattpocock/implement` calls `code-review`), tell that step to skip it: the review is a step of its own, on the other family. Tell it too to commit its work before the step ends, since the review reads `git diff <base commit>...HEAD`. Say in the step note that its internal review was skipped (`code-review: skipped, the review runs cross-family`).

**Per-item cost.** When the change adds work repeated per item (per row, per record, per option of a relation, per request), tell the implementation step to measure it before it delivers: run the affected path under a representative load (the data size the feature meets in use, or the project's largest fixture) and compare with the base commit, measuring the actual work (time, calls made, rows or bytes processed, allocations), not only the query count. Use what the project already has (its test runner, a script, a timer around the call); no benchmark framework. Record it with `scripts/state <target repo> check <n> pass|fail --command "<what ran>" --env "<environment>" --scope <paths>` and put the numbers in the step note. A cost that grows beyond what the task accepts is a finding.

## Manual checklist

What the change really does, as points to check: built from `git diff <base commit>...HEAD` and the step notes, read against the issue (or spec), so it shows what was changed, not only what was asked; a requirement with no change behind it is a point too.

- One line each: where (page, URL, command) → action → expected result, naming the login or seed data it needs.
- At most 15 points, the riskiest first (user-facing behaviour, data, permissions, then the rest); what does not fit goes in one closing line, `Also changed: …`.
- Tag each point `[agent]` when a command, a test, an HTTP request or a scripted browser can show the result, `[you]` when it needs a person's eye or judgment (layout, responsive, themes, copy, real data).
- The checklist is a help, never a gate: the user may skip it.

## Implementation outcome

When the implementation step ends, show a concise outcome with the files changed since the base commit and the manual checklist, then start the review. Leave `[you]` points for the PR; they do not block its creation or count as passed. If the user explicitly requested a check here, wait on the next unfinished step, fix and commit what they report, then resume under [autonomy.md](autonomy.md). The check is a pause, not an extra step.

## Reviews, security and fixes

The review, then framework-review when it runs, the security check, and independent-review when on, each in its own fresh subagent on the reviewers' family ([cross-family-review.md](cross-family-review.md)).

**One pass per purpose.** The cross-family review is mandatory ([ADR 0001](../../docs/adr/0001-single-cross-family-review.md)); framework-review, security and independent-review each have their own purpose, the one their step's summary declares. Any other pass on a review step (a re-check after fixes, the decisions after them) declares what it adds with `scripts/state <target repo> expect <n> --purpose "<what it checks that the earlier passes did not>"`, and `expect` refuses a second pass without one or for a purpose already served. Never rerun a review for reassurance.

**Findings.** Consolidate the findings of every review that ran into one list: one entry per distinct problem, with the step ids that reported it, and give each a severity: `critical` wrong results, data loss or a security hole; `high` a bug or risk a user will meet; `medium` a real but contained problem; `low` style, naming, small clean-ups. Validate findings against the code and approved spec. Fix confirmed problems within scope automatically; record false positives as `declined` with evidence, and unrelated improvements as `deferred` with the reason. A finding that requires a material decision or scope change follows [autonomy.md](autonomy.md); severity alone is no reason to ask which findings to fix. Keep every finding and its disposition for the run record. Each review delivers its findings as a `findings` artifact ([step-result.md](step-result.md)), without decisions: deciding is yours, not the reviewer's, and `deliver` refuses a review's own decisions before its `fixes` verdict. A review with any finding delivers the verdict `fixes`, so it goes to the fixes (or to your declined and deferred decisions), never straight to the pull request; after them, `expect <n> --purpose "record the decisions after the fixes"` and deliver the findings with their decisions and the verdict `done`.

**Conditional security check.** Inspect the diff for auth, user input, queries, secrets, new dependencies, config and permissions (the `use_when` of the `security` candidate). When any appear, or the task is security- or data-sensitive or the user explicitly requested security, announce why and run its preselected skill. Otherwise close that conditional step as `skipped` with the reason. A triggered check with no usable candidate is a missing-capability exception. Security is review-only; changes it proposes follow the findings policy.

**Fixes.** In-scope fixes run like a skill step, in a new subagent on the implementation step's model (without subagents, in the main session): it gets the findings, approved scope, execution policy, handoff and step notes, fixes them (test-first where a test can show the problem), runs the affected checks first, commits, and writes its note to `.router/steps/<n>-fixes.md`, with `n` the coordinating step's position. It saves progress on the coordinating step as SKILL.md §6 point 5 says (`check <n>` per check, `progress <n>` after each commit), so an interrupted fix resumes from its record ([resume.md](resume.md) **Interrupted step**). That step stays `running` until the fixes and checks finish, so a pause or resume does not drop them. When a fix materially changes behavior and invalidates earlier review evidence, re-check that change once in a fresh reviewer, declared with `expect <n> --purpose "re-check <the change>"`: a cross-family review too, since the fixes ran on the implementation's family ([cross-family-review.md](cross-family-review.md)). A fix that does not change behavior gets no further review pass. Continue to the next step once the findings are resolved or explicitly accounted for; an unresolved correctness requirement is a blocker, not a deferred improvement.

## Verification (when on)

Start a fresh subagent (without subagents, the main session) that has not seen the implementation: it gets the target repo path, the handoff, the manual checklist and the execution policy. It works through the `[agent]` points only, never edits tracked files, and for each reports `pass`, `fail` or `could not check`, with the evidence (the command and its output, the response, a screenshot path). Its note goes to `.router/steps/<n>-verification.md`, and each result it reaches is recorded as it goes with `scripts/state <target repo> check <n> …`, its scope the files the point depends on, so an interruption keeps the points already shown. Handle a `fail` like a finding: fix in scope, rerun the affected verification, and escalate only an exception. A required check that cannot run is a blocker; optional manual acceptance remains documented. Tick only `[agent]` points that passed and mark them `verified by agent`.

## Pull request

Run the project's required checks on the final changes, resolving recoverable failures before delivery. A required check recorded on the implementation, fixes or verification step is not run again when `scripts/state <target repo> recover --env "<this environment>"` lists it as `reuse:` (same files, same environment); without `--env` nothing is reused, every other one runs, and none is skipped. Commit the remaining authorized changes and push the work branch, preserving unrelated work. Prepare the PR as a delivery of the pull-request step ([step-result.md](step-result.md)): `expect` it, and have the `pull-request` skill write the body to the `pr-body` path and the consolidated findings, each with its decision (`[]` when there are none), to the `findings` path; `deliver` checks both before anything is published. The body links the issue with `Closes #<issue>` (issue-free: [issue-free.md](issue-free.md)) and ends with the manual checklist, updated for the fixes since. Open the PR under the existing workflow authorization, with the accepted body as it is (`--body-file "$(scripts/state <target repo> artifact pull-request pr-body)"`); if the implementation already opened a draft PR, update that PR and mark it ready when the required work is complete. Record its number and URL with `scripts/state <target repo> handoff pr <number> <url>`.

Then write the run record (what ran and what the reviews found, read back by `scripts/stats`) into the PR with `scripts/record <target repo> --pr <number> --findings <file> --checklist <points>,<agent>[,<passed>,<failed>] --session-model <id>`, adding `--tokens` / `--cost` only when the harness or tool reported them. It takes the steps, skills, models and efforts from the state; you give it what only you know: the findings file (by default the accepted `findings` of the pull-request step), a JSON array with every review finding as `{"title": one line, "severity", "found_by": [step ids], "decision"}`, and the checklist counts. It refuses invalid input with the reason; without `--pr` it prints the block instead.

After the record is written, close the PR step with its outcome, report the URL, local check results, observed CI status and outstanding manual acceptance, and stop. Distinguish CI still running or unavailable from passed checks. The user merges. `scripts/stats` adds the records of a repo's PRs up.
